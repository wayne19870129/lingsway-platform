# ADR-032: 执行者退回 Codex 桌面版；ChatGPT 重新承担指挥；放弃"无人值守"目标

- 状态: **已接受（Accepted）**
- 日期: 2026-09-19
- 决策范围: ADR-030（Claude 承担派发）、ADR-031 §1（执行者模型前提）、
  `docs/85` §0 与 §2、`docs/86` 全文。
- 触发来源: Codex Cloud 实测不可用（额度与模型档位均不可控），User 决定
  退回「ChatGPT 网页版做大脑 + Codex 桌面版执行 + Claude 定期审查」。

## 1. 先更正 ADR-031 §1 的一个事实错误

ADR-031 §1 那张表把执行者写成 **「5.6 Luna，轻推理」**，并把它当作整条
决策的**前提**。**这个前提没有被验证过，而且现在有反证：**

- 2026-09-19，Codex Cloud 被直接问到时自报 **「GPT-5.6 Sol」**，不是 Luna；
- Codex Cloud 的环境创建与设置页面**没有模型选择器**，用户无法指定；
- 它同时明确表示**无法读取或证明**平台为该次运行设置的 `reasoning effort`。

（最后一点它答得对：模型自报身份本身也不是可靠证据。所以正确的结论不是
"其实是 Sol"，而是**"执行者的型号与推理档位既不可控、也不可验证"**。）

**真正成立的前提，是能力不对称这件事本身**——指挥侧推理强、额度宽，执行侧
两者都弱——而不是任何具体产品名。ADR-031 的结论（判断在指挥侧、执行侧只
照着做、指令卡要写到不需要思考）**不受影响，依据被换成可验证的那一条**。

**教训单独记一笔：把一个无法验证的事实写进 ADR 的"前提"栏，会让整条决策
看起来比实际更有依据。** 以后前提栏只写能验证的东西；不能验证的写进
"未验证假设"，并说明如果它不成立会怎样。

## 2. 为什么放弃 Codex Cloud

两条，都是实测：

1. **额度不够，且无法只用便宜档位。** 页面不提供模型/推理强度选择，
   所以"用轻推理省额度"这个策略**根本无法实施**。
2. **它自己推不了分支。** 沙箱没有 git 凭据
   （`fatal: 'origin' does not appear to be a git repository`），
   每个任务都必须人工点一次"Create PR"。

第 2 条本身可以忍；第 1 条不能——ADR-031 的整个成本模型建立在"执行侧用
便宜档位"上，而那个开关不存在。

**要公平记一句：Codex Cloud 的行为是合格的。** 它守住了「允许修改的文件」
清单、跑完了全部验收命令、贴了真实输出、推送失败时诚实上报、没有 TASK 时
拒绝动手。**不通的是这条路的平台约束，不是执行者的纪律。**

## 3. 新分工

| 角色 | 负责 | 不负责 |
|---|---|---|
| **User** | 业务需求、验收、合并治理/审计 PR、**开着电脑** | 写代码 |
| **ChatGPT 网页版**（大脑） | 读派发队列选任务、把任务交给 Codex 桌面版、审查 PR、写指令卡 | 写 TASK/ADR；改代码；合并 |
| **Codex 桌面版** | 按 TASK 实现、跑验证、建分支、提 PR、按指令卡返工 | 决定做什么、扩大范围、自行合并 |
| **Claude Code** | 架构、撰写 ADR 与 TASK、~~定期监督~~ **User 下令时审查**（ADR-033）、必要时拉闸 | 日常实现；实时盯过程；合并 |
| **GitHub workflow** | 条件全满足时机械合并 | 做任何判断 |

**ADR-030 把派发权移给 Claude 的那一条，本 ADR 予以撤销。** 派发回到
ChatGPT。

### 3a. 那 ADR-030 §2 的安全论证怎么办

ADR-030 把派发移给 Claude，是为了消除 ADR-029 记录的反对意见 #1：
**审查者在审查自己规格下产出的代码**。现在派发回到 ChatGPT，这个问题会
回来吗？

**不会，只要 TASK 文件仍然由 Claude 独占撰写。** 关键区分是：

- **"派发"** = 把已经写好的 TASK 交给执行者去做 —— 谁做都行；
- **"规格"** = TASK 文件里的目标 / 约束 / 允许修改的文件 / 验收标准 ——
  **这才是审查的判据**。

ChatGPT 审查时对照的是**它没有写的那份 TASK**。独立性保在规格这一层，
不在派发动作这一层。**所以 `AGENTS.md` 写权限表里"`docs/82-tasks/` 与
`docs/80-decisions/` 由 Claude Code 独占"这条，是本次调整能够成立的唯一
理由，不得随之放松。**

## 4. 放弃"无人值守"这个目标，明确写下来

Codex 桌面版跑在 User 的电脑上。**因此：**

- **User 的电脑不开，整条流水线就不前进。** 这是本 ADR 接受的代价。
- 之前几次讨论里出现过"以后就不用开电脑了"的说法，**从本 ADR 起不成立**，
  不要再按那个前提设计任何东西。

**仍然不需要电脑的部分**（这些在云上，与执行者无关）：CI、自动合并、
健康摘要、Claude 的监督。

## 5. Codex Cloud 的代码审查：**一并关闭**（本节已更正）

> **更正记录：本节初稿写着"保留，零代价"，理由是"它不消耗执行侧额度"。
> 那句话是我没有验证就写的，而且是错的。**
>
> 证据在 Codex 的分析页上，一句话：**「Codex 和工作共用同一用量限额。」**
> 也就是说 ChatGPT、Codex 桌面版、Codex Cloud、以及 Cloud 的代码审查
> **全都吃同一个池子**。代码审查不是白送的，它在跟执行抢额度。
>
> 这是本轮第二次犯同一类错误——**把没验证的东西当作论证的支点**
> （第一次是 §1 的模型名）。两次都朝"让方案显得更划算"的方向偏，
> 这个偏向值得单独记住。

**决定：跟执行一起关掉 Codex Cloud。**

额度是本项目当前的硬约束（2026-09-19：每周剩 12%，剩余额度 0）。在一个
共用池子里，代码审查每跑一次，就少一次 Codex 桌面版的执行机会。
**执行是不可替代的，审查有替代品（ChatGPT）——所以该砍的是审查。**

**但要如实记下被放弃的价值，不要假装它没用：**

它在 PR #142 上抓到过一个真实的跨步骤逻辑缺陷（比较基准读错分支，会导致
每 2 小时一次空提交），那不是格式问题，是 ChatGPT 当时没看出来的东西。
**关掉它 = 少一双独立的眼睛**，这是用能力换额度，不是"去掉一个没用的东西"。

**重新打开的条件**：额度不再是瓶颈时（例如套餐升级、或周额度稳定有余量），
应当重新打开——它没有判定权（`author_association` 是 `NONE`，闸门不认它的
verdict，已实测），所以打开它不会引入新的风险，只会多一层检查。

### 5a. 开关在哪（2026-09-19 记录，免得重开时重新找）

`chatgpt.com/codex` → **设置** → **代码审查** → 下方「**代码仓库首选项**」
表格里 `wayne19870129/lingsway-platform` 那一行：

| 列 | 作用 | 本次设置 |
|---|---|---|
| **自动代码审查** | **要不要审——额度烧在这里** | 「审查我的 PR」→ **「遵循个人设置」** |
| 审查触发条件 | 什么时机审 | 保持「遵循个人设置」 |
| 全面代码审查 | 审的时候挖多深 | 保持「遵循个人设置」 |

**只动「自动代码审查」这一列。** 「全面代码审查」只控制深度，把它关掉
**审查照样会跑**，省不下额度——重开时同理，要动的也是第一列。

**这一列没有「关闭」选项**（本节初稿写着改成「已关闭」，是没看界面凭想当然
写的，实际下拉只有三项）：

```
审查所有 PR    所有贡献者的 PR 都审
审查我的 PR    只审你自己提的 PR   ← 本次之前就是这个
遵循个人设置    跟随页面顶部的「自动审查」总开关
```

**关闭的做法是选「遵循个人设置」，并保持顶部「自动审查」总开关关着**
（2026-09-19 实测它本来就是关的）。

### 实际执行了两步，不止这一步（2026-09-19 补记）

关闭这件事实测下来是**两层**，只关一层不够：

| 层 | 做了什么 | 效果（实测） |
|---|---|---|
| **执行** | **删掉了该仓库的 Cloud 环境**（`chatgpt.com/codex/cloud/settings/environments`） | 触发仍会发生，但跑不起来。PR #149 上它回的是「To use Codex here, create an environment for this repo.」——**模型没跑，额度没烧** |
| **触发** | 「自动代码审查」改为「遵循个人设置」 | 从源头不再产生 `GitHub Mention` 任务 |

**只删环境不关触发**：每个 PR 仍会在 Codex 任务列表里生成一条条目、并在
PR 上留一句「create an environment」噪音评论。是噪音，不是成本。

**所以重新打开时也是两步，不是把下拉改回去就行**：先重建环境，再把
「自动代码审查」改回「审查我的 PR」。§5 写的"额度宽裕后应当重新打开"
要按这两步执行。

**明确没有做的一步**：**没有**去 GitHub 撤销 Codex App 对本仓库的权限。
原因是**无法确认 Codex 桌面版提 PR 是否走同一个 GitHub App**——桌面版是
本 ADR 选定的执行者，不能为了关掉 Cloud 而冒险打断它。上面两步已经够用，
且都可逆。**这一条是"不确定就不做"，不是"已确认无影响"。**

> **这个做法有一处脆弱，记下来免得以后查半天**：选了「遵循个人设置」之后，
> 本仓库审不审就**挂在那个全局开关上**。哪天为了别的仓库把顶部「自动审查」
> 打开，`lingsway-platform` 会**跟着一起恢复审查**，且没有任何提示。
> 这与铁律 8 更正里记的是同一类问题：**把约束寄托在仓库管不到的设置上**。
> 因此关闭之后要实际验证一次（看后续 PR 有没有 Codex 的审查评论），
> 而不是看着下拉框的值就当已经关了。

**不要用"去 GitHub 卸载 Codex App / 撤仓库权限"那条路来关它**：那条路要
重新授权、重新配仓库才能恢复，与本节"额度宽裕后应当重新打开"的意图冲突。

## 6. 不做的事

- **不把 TASK / ADR 的撰写权交回 ChatGPT**（ADR-029 §7 不变，且它是 §3a
  成立的前提）。
- **不放宽 ADR-029 §4 的六个合并条件**，不放宽 3 轮返工上限，
  不放宽铁律 1–7。
- ~~**不弱化 ADR-030 的定期监督**~~——**2026-09-19：本条被 ADR-033 撤销。**
  ADR-031 §3 记录的"执行端没有冗余校验"这个性质**确实没变**，ADR-033 也没
  否认它；它主张的是这个缺口当前由"每个 PR 都由 User 人工合并"补着，
  并写明该前提消失时必须恢复（ADR-033 §8）。
- **不再声称流水线可以无人值守**（§4）。
- **不再声称"全自动"是这个阶段的目标。** User 已明确：ChatGPT 网页版 +
  Codex 桌面版 + 人工复制粘贴，**自动化这一步先不做**。继续按"全自动快到了"
  去设计，只会再造出一批依赖不存在能力的东西——本轮已经造过两次
  （Routine 载体、Codex Cloud），两次都是这么来的。

## 6a. 当前真实的交接方式：人工中继

**这一节是为了防止后来者误以为中间有自动化。**

```
Claude 写 TASK/ADR（仓库里）
  → ChatGPT 读队列、写派活指令
    → **User 复制粘贴** → Codex 桌面版执行、提 PR
      → ChatGPT 审查、写指令卡
        → **User 复制粘贴** → Codex 返工
          → 条件满足 → workflow 机械合并
```

**两处"复制粘贴"是人工的，没有自动化，短期内也不打算做。**
云端仍然自动运行的只有：CI、自动合并、健康摘要、Claude 的监督。

### 6b. 同日移除派活用的 Issue 模板

`.github/ISSUE_TEMPLATE/codex-dispatch.md` **已删除（2026-09-19）**。

它是唯一一条走 Issue 的派活路径，三个前提同时不成立：

1. **`@codex` 在 Issue 上不触发任何东西**（实测，`docs/85` §2 已记录）；
2. Codex Cloud 已按本 ADR §2/§5 弃用，没有任何执行者在监听 Issue；
3. `AGENTS.md`（2026-09-18，User 决定）已写明**唯一的记录载体是
   `docs/82-tasks/TASK-*.md`**，并明确只保留 `incident.md` 与
   `external-fact.md` 两个模板——那条例外本身就已经把这个模板排除在外了。

**它不是无害的**：2026-09-19 实际用它建出了两条没人读的 Issue
（#138 / #139，同一个 TASK 重复派发两次），已连同模板一并关闭/删除。
这是一条**看起来还在工作、实际上谁都不读**的载体，正是本仓库反复被咬的
两份事实源问题的另一种形态——只是这次第二份是空的。

`ADR-029 §2`「Issue 是触发器，TASK 文件是权威」中的**前半句**由此失效；
**后半句仍然成立且更重要了**：现在只剩 TASK 文件一个权威。

## 7. 重新评估条件

- 若 Codex Cloud 将来开放模型/推理强度选择**且**额度可用，可以重新评估
  §2——但要先补一次实测，不要凭页面上出现了选项就认定可用。
- 若 ChatGPT 的派发与审查之间出现"为了让自己的派发通过而放松审查"的迹象，
  §3a 的论证即告失效，派发权必须再次移走。
- 若"必须开电脑"成为实际瓶颈（任务积压肉眼可见），重新评估执行者的选择，
  而不是重新评估 §4 的诚实记录。
