# ADR-030: Claude Code 作为编排大脑（架构 + 派发 + 监督 + 停机权）

- 状态: **已接受（Accepted）**
- 日期: 2026-09-19
- 决策范围: ADR-029 §1（流水线角色）、§6（定时审计的触发机制）、
  `AGENTS.md`「协作角色与职责」、`docs/85` / `docs/86` 的角色表。
- 触发来源: User 明确要求 Claude 承担「终极大脑」角色——设计架构、激活
  ChatGPT 与 Codex、**定期**（而非实时）监督、发现问题时叫停并重新规划；
  同时明确要求 **Claude 的 token 消耗要低**，干活主要由 ChatGPT 和 Codex 承担。

## 1. 这条 ADR 改了 ADR-029 的什么

| 角色 | ADR-029 | 本 ADR 起 |
|---|---|---|
| 写 ADR / TASK | Claude | Claude（不变） |
| **读队列、建 Issue 派活** | **ChatGPT** | **Claude** |
| 审查 PR（固定格式、精确 head SHA） | ChatGPT | ChatGPT（不变，且成为它唯一的职责） |
| 实现代码 | Codex | Codex（不变） |
| 执行合并 | GitHub workflow | 不变 |
| 定期监督、叫停、重新规划 | 无此角色（只有每 6 小时的审计） | **Claude** |

ADR-029 §6 的定时架构审计**并入**本 ADR 的监督循环，不再是独立机制。

## 2. 为什么这样更好，而不只是"换个人做"

ADR-029 自己记录的第 1 条反对意见是：**「ChatGPT 将审查自己规格下产出的
代码，main 之前再无独立检查。」** 那条反对意见在 ADR-029 下是成立的且没有被
消除，只是被 User 知情接受了。

把派发权移给 Claude **恰好消除了它**：需求由 Claude 写（TASK/ADR），代码由
Codex 写，审查由 ChatGPT 做。**规格作者与审查者不再是同一个 agent。**
这是安全姿态的实质改善，不是角色轮换。

同时它消掉了一个已经出过事的中继环节：ADR/TASK 变更靠聊天转述给 ChatGPT，
ChatGPT 再转述给 Codex。本仓库已经因为"两份真相源"吃过多次亏
（`docs/85` §5.8 的两次撞号、§5 曾被写进聊天消息而不是文件）。少一次转述
就少一次漂移。

**对 ADR-029 §7 的那条理由（"让下达任务的人同时定义约束自己的规则，会让
护栏失去意义"）的处理：** 那条理由的真正保护对象是**执行者**——
「允许修改的文件」是约束 Codex 的，不是约束 TASK 作者的。Claude 不执行，
所以 Claude 同时写 TASK 和派发不触碰那条护栏；被约束的一方仍然是另一个
agent。ADR-029 §7 的裁定（三个 docs 目录 Claude 独占）**继续有效**。

## 3. 监督机制：机器采集事实，Claude 只做判断

**这是本 ADR 最重要的工程决定，直接来自 User 的 token 预算要求。**

让 Claude 每次监督都去爬仓库、列 PR、读 CI 日志，成本高且大部分轮次的
结论是"没变化"。因此拆成两层：

| 层 | 谁 | 成本 | 做什么 |
|---|---|---|---|
| 采集 | `.github/workflows/pipeline-health.yml`（**无 LLM**） | 接近零 | 把流水线状态压成一份定长摘要 |
| 判断 | Claude，低频唤醒 | 只读那份摘要 | 继续 / 调整架构 / 叫停 |

摘要必须是**定长、可机读、自带异常标记**的，让 Claude 在不展开任何 PR、
不读任何日志的情况下就能判断要不要介入。具体字段与落地方式见
`docs/82-tasks/TASK-S10-pipeline-health-digest.md`。

**这一层刻意不依赖 `CLAUDE_CODE_OAUTH_TOKEN`。**

> **2026-09-19 更正（原文写过头了，此处按事实改写）。** 本节原本写着
> 「没有任何证据表明该 Secret 已配置可用」。**这句话是错的。** 远端存在
> `claude/issue-66-*`、`claude/issue-97-xray-gateway-registry-wiring` 等一批
> 分支，而 `claude-code-action` **只有真正运行并提交之后**才会产生这种分支
> ——所以它历史上确实工作过，Secret 至少在 2026-09-12~14 期间是可用的。
>
> 准确的事实是：`claude.yml` 有 247 次运行，**近期**全部 `conclusion: skipped`，
> 原因是它的 `if` 要求评论含 `@claude`，而最近没有这样的评论——
> **是没被触发，不是凭据坏了。**

即便如此，健康摘要仍然只用 `GITHUB_TOKEN`、不调用任何 LLM，理由有两条，
都与凭据是否可用无关：

1. **成本。** 每 2 小时一次 LLM 调用，绝大多数轮次的结论是"没变化"，
   这正是 User 的 token 预算要反对的东西。
2. **依赖面。** 采集层是判断层的唯一输入；让它依赖一个可能过期、可能被
   轮换、且无法在仓库里被检查的 Secret，等于把监督的可用性绑在一个仓库
   之外的状态上——这与 §3a 刚刚学到的教训是同一条。

### 3a. 被替换的机制，以及它为什么失败（诚实记录）

ADR-029 §6 的审计原本由一个 claude.ai Routine（`43 */6 * * *`）触发。
2026-09-19 00:43 它**确实触发了**（会话 `cse_01CvtKzoF3Tp3mauatU85GQP`），
但 45 分钟后 `last_run.status` 仍为 `PENDING`，`claude/audit-*` 分支不存在，
没有任何 PR。按提示词自身的规定它**不该跳过**（continuity 里无审计记录 ⇒
视为从未审计 ⇒ 走完整流程），所以这不是空转，是卡住。

原因：创建该 Routine 的会话没有 connector 授权，触发出的会话拿不到
`mcp__github__*`，也没有仓库源——读不到代码，也开不了 PR。

**教训写进架构，而不是只修那一个 Routine：任何"定期自动化"的载体，如果它
的凭据与仓库访问不是版本受控、可在仓库里被检查的，就不能作为安全机制的
承载者。** 健康摘要放进 `.github/workflows/` 正是为此。

## 4. 监督节奏

- **默认低频**：健康摘要每 2 小时由 workflow 生成（机器，成本可忽略）；
  Claude 的判断轮次按需，不追求实时。
- **实时观测已明确不做。** User 的要求是"不需要实时观测过程"。Claude 不订阅
  每个 PR 事件、不逐轮跟审查往返——那是 token 的主要浪费来源。
- **强制介入节点**（这些不等排期，见到就做）：
  - 健康摘要出现任一 §5 的停机信号；
  - 接线任何真实外部系统之前（Webshare / Mihomo 生产激活）；
  - 任何生产部署之前；
  - 一条工作线（如整个 S04）完成之后。

## 5. 停机信号与处置（Claude 的停机权）

| 信号 | 处置 |
|---|---|
| 审计发现 Critical（数据损坏 / 凭据泄漏 / 客户可踩到的业务错误 / 铁律被绕过） | **拉闸** + 明确告知 User |
| `main` 上 CI 变红 | **立即拉闸**（`main` 是所有 PR 的基线，红的基线会污染后续全部判断） |
| ChatGPT 给了 PASS，但监督在同一个 SHA 上发现 Critical | **拉闸** + 触发 ADR-029「重新评估条件」 |
| 同一个 finding 连续两次修复失败 | 给该 PR 打 `no-automerge`，重新规划这一项 |
| 单个 PR 返工到 5 轮 | 给该 PR 打 `no-automerge`，交给 User |
| 连续 3 个 PR 自动合并且 User 全程未参与 | 暂停派发，出一份进度汇报（`docs/85` §6.2 格式） |
| 某 PR 开着超过 12 小时、无新提交、仍有未解决 findings | 视为卡住：诊断根因、改 TASK、重新派发 |

### 5a. 停机是单边的，复机不是

**Claude 可以独自停掉流水线，但不能独自恢复它。**

- 拉闸：把 `.github/automerge-enabled` 置为 `false`，走一个普通 PR
  （因此有记录、可追溯）。Claude 可以自行发起。
- 复机：必须 (1) 写清根因，(2) 修掉放行了这个问题的 ADR / TASK / 闸门，
  (3) 恢复开关的那个 PR **由 User 人工合并**，(4) 然后才重新派发。

这个不对称是本 ADR 的核心安全属性。**能自己开机的自动化，断路器等于不存在。**

## 6. 不做的事

- **不做实时观测**：不订阅每个 PR 事件，不跟每一轮审查往返。
- **不把判断层做成 Actions 里的 LLM 任务**：那会把"低频判断"变成
  每 2 小时一次的 30-turn 调用，与 token 预算相反，且依赖未验证的 Secret。
- **不放宽 ADR-029 §4 的六个条件**，不放宽 5 轮上限，不放宽铁律 1–7。
- **不给 Claude 合并权**。Claude 派发、监督、停机；合并仍由 workflow 机械
  执行，治理/审计 PR 仍由 User 人工合并。
- **不让 ChatGPT 再写 TASK 或 ADR**（ADR-029 §7 不变）。
- **不删除 `docs/85`**：它仍是 ChatGPT 的常驻指令，只是职责收窄为审查。

## 7. 重新评估条件

- 健康摘要连续多次未能预警一个后来被人工发现的问题 ⇒ 摘要字段设计不足，
  重新评估第 3 节。
- Claude 的监督轮次开始频繁到与"实时观测"无区别 ⇒ 说明停机信号设计得太
  灵敏或流水线本身不稳，重新评估第 4、5 节。
- 出现一次"Claude 拉闸后又自行恢复" ⇒ 第 5a 条被违反，这是架构失效而不是
  操作失误，必须重新评估。
- 若 `CLAUDE_CODE_OAUTH_TOKEN` 被确认可用，可以重新评估是否把部分采集
  工作交给 Actions 里的 Claude——但**判断层仍不应放进定时 LLM 任务**。
