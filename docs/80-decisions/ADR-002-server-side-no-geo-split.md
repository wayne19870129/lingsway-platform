# ADR-002: 服务端网关不做地理分流，分流规则（若启用）下沉到客户端

- 状态: 已接受
- 日期: 2026-09-10（补记，实际生效于 T3/T5）

## 问题

客户国内外流量的分流可以在两处实现：Xray 网关侧（服务端）按目的地做路由，
或者在客户端（Clash/Mihomo 配置的 `rules`）按域名/IP 段分流。两者都能降低
不必要的流量经住宅出口转发，但风险和可回退性完全不同。

## 决定

Xray 服务端网关只负责“已认证流量转发到指定出口”，不做按地理位置的分流
判断；`geoip:private → BLOCK`、`tcp,udp → BLOCK` 这两条服务端路由安全
不变式（见 `backend/tests/guards/test_routing_invariants.py`）只是拒绝
私网探测和未匹配流量，不是地理分流。真正的“国内流量走 DIRECT、国外流量
走代理”这类分流，如果要做，只能通过客户订阅的 Clash `rules` 字段下沉到
客户端本地判断（即 TASK-T13 覆盖的范围），服务端网关的渲染逻辑不参与、
也不感知这类判断。

## 约束

1. `ops/gateway/render_xray_routes.py` 与 `providers/gateway/xray_file.py`
   不得引入基于 GEOIP/GEOSITE 的服务端路由分支。
2. 客户端分流规则的启用、灰度、回退完全由 `docs/82-tasks/TASK-T13-split-routing.md`
   和 ADR-012 管理，服务端安全不变式（private BLOCK、tcp/udp BLOCK 兜底）
   不受客户端分流开关影响。

## 考虑过的替代方案

1. 服务端按 GEOIP 分流后再转发：网关需要维护 GEOIP 数据库版本、承担更多
   路由状态，且一旦分流误判会直接影响所有客户，回滚需要走九步安全重载，
   风险远高于客户端本地分流（客户端分流可以单订阅灰度、单客户端回退），
   否决。

## 后果

服务端网关逻辑保持简单、可预测，风险集中在客户端分流这一个可灰度的
变更点上。代价是国内流量在客户端分流规则未启用前会继续经过住宅出口。

## 重新评估条件

当客户端分流规则（T13）经过灰度验证并全量启用后，若发现某些场景必须
由服务端介入（例如需要按订阅整体强制切换出口而非按域名），重新评估是否
需要有限度的服务端路由能力。
