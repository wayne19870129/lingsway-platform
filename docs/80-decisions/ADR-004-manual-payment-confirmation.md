# ADR-004: 支付保持人工确认，不接支付 webhook

- 状态: 已接受
- 日期: 2026-09-10（补记，实际生效于 T3）

## 问题

订单收款可以由支付渠道的 webhook 自动确认，也可以由管理员人工核对到账后
点击确认。当前客户规模下选哪一种。

## 决定

`PaymentProvider` 保持 `manual` 实现：`verify_webhook()` 直接
`raise NotSupported`，收款确认统一走 `POST /admin/orders/{id}/confirm-payment`
的人工路径（`backend/app/api/admin.py`），确认后触发 `domain/provisioning.py`
的九步开通编排。

## 约束

1. 不实现任何支付渠道的 webhook 签名校验或自动确认逻辑。
2. `PaymentProvider.confirm_manual()` 是唯一允许把订单标记为已付款的入口，
   不提供第二条自动化路径。
3. 购买、续费、支付、账单类端点在客户端最底层硬拦截（见 `webshare.py` 的
   写操作白名单），不受本 ADR 影响，因为那是对外部供应商的拦截，不是对
   自家支付渠道的拦截。

## 考虑过的替代方案

1. 接入微信/支付宝官方 webhook：客户量小时，人工确认的响应时间
   （Telegram 通知 + 几分钟内人工核对）足够，而 webhook 需要额外维护
   签名校验、幂等消费、渠道账号资质等成本，且金额相关的自动化路径一旦
   出错难以追责，否决。

## 后果

每笔订单从客户点击“我已付款”到实际开通之间存在人工确认的等待时间；
换取的是不给自动化金钱路径留后门，符合仓库“购买/续费/支付/账单类端点
不提供 force/override”的铁律精神。

## 重新评估条件

当订单量增长到人工确认成为响应速度瓶颈时，重新评估接入官方 webhook，
且必须先有独立的签名校验与幂等消费护栏测试再接入。
