# ADR-003: Xray 不启用运行时 gRPC 热添加

- 状态: 已接受
- 日期: 2026-09-10（补记，实际生效于 T4）

## 问题

Xray 支持通过 gRPC API 在不重载进程的情况下动态增删 inbound/outbound/路由，
理论上可以让“新客户开通”不必触发一次全量安全重载。是否要在
`providers/gateway/xray_file.py` 里接入这条路径。

## 决定

当前不实现 gRPC 热添加。所有配置变更（包括单个客户开通/退订）一律走
`ops/gateway/safe_reload.py` 的九步安全重载（备份 → 全量渲染 → JSON 校验
→ `xray run -test` → 保全校验 → 重载 → 健康检查 → 失败回滚 → 审计日志），
不提供绕过九步保护的第二条路径。

## 约束

1. `providers/gateway/xray_file.py` 的 `apply()` 只能调用九步安全重载，
   不得直接调用 Xray gRPC 客户端做增量变更。
2. 若未来引入 gRPC 热添加，新路径必须同样满足“候选配置校验失败绝不生效”
   与“保全现有用户路由”这两条不变式，不能因为是热添加就跳过校验。

## 考虑过的替代方案

1. 用 gRPC 增量添加新客户的 inbound：能减少重载频率和抖动窗口，但会让
   “数据库全量生成配置”（铁律第 1 条）和“gRPC 侧内存状态”出现两份可能
   不一致的真相来源，且增量路径缺少全量渲染那样的保全校验，一旦出错难以
   审计和回滚，否决。

## 后果

客户量上升后，每次开通/退订都会触发一次全量重载，重载耗时和抖动会随
配置规模增长；这是用可回滚性换来的代价，属于有意选择。

## 重新评估条件

当客户规模增长到全量重载的耗时或抖动开始影响存量连接的可用性时，重新
评估是否需要 gRPC 热添加，并且必须先补齐与九步安全重载等价的校验与
回滚能力。
