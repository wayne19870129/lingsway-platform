# ADR-031: 思考与执行分离（ChatGPT 想，Codex 做），返工上限 5 → 3

- 状态: **已接受（Accepted）**
- 日期: 2026-09-19
- 决策范围: ADR-029 §1（流水线各环节职责）、ADR-030 §5（停机信号）、
  `CLAUDE.md` 的返工轮次上限、`docs/85` §3、`docs/86` §5。
- 触发来源: User 指出当前配置把最强的模型闲置、把判断压在最弱的模型上，
  并要求把返工上限从 5 轮降到 3 轮。

## 1. 实际的资源分布（这是决策的前提，不是背景）

| 执行者 | 模型 | 额度 |
|---|---|---|
| **ChatGPT 网页版** | 5.6 Soar，**高推理** | 近乎无限 |
| **Codex Cloud** | 5.6 Luna，**轻推理** | 紧张（2026-09-19 实测：每周额度剩 12%，剩余额度 0） |

**强模型 + 大额度的那一个在闲着，弱模型 + 小额度的那一个在做判断。**
这不是"可以优化一下"，这是配置反了。

**而且轻推理不是偏好，是约束。** Codex 要真的执行任务（读仓库、改文件、
跑测试、推分支），这件事本身就耗额度；在额度有限的前提下，**只有轻推理
档位才跑得完一个完整任务**。所以"Codex 用弱模型"不是一个可以在方便时
调回去的选择，而是这条流水线必须长期承受的事实。

这反过来决定了架构必须**假定执行者是弱的**，而不是把它当成临时状态——
下面 §3 的代价因此是永久性的，不是过渡期的。

## 2. 决策

**一切判断在 ChatGPT，一切执行在 Codex。**

| 谁 | 做什么 | 明确不做什么 |
|---|---|---|
| **Claude Code** | 架构、ADR/TASK、监督、停机 | 实现；实时盯过程 |
| **ChatGPT（5.6 Soar 高推理）** | 审查 PR；**把该改什么写成逐条可执行的指令卡**；把两者合并成一条 PR 评论 | 写 TASK/ADR；改代码；合并 |
| **Codex（5.6 Luna 轻推理）** | **照着指令卡改**；跑验证；推同一分支 | 自己判断该不该改、该怎么改 |

**不让 Codex 思考，只让它执行。**

## 3. 这为什么同时提高质量，而不只是省额度

省额度是结果，不是理由。真正的理由是**能力匹配**：

**轻推理模型做「照着改」，比做「想清楚该怎么改」可靠得多。** 把判断从
Luna 手里拿走，等于把它放回它擅长的那一格。产出质量是**上升**的，不是
用质量换成本。

**但必须诚实记录代价，否则这条 ADR 是在自欺：**

> **指令卡越具体，Codex 越像一只手——如果指令本身是错的，它不会拦住。**

一个高推理的执行者可能会说"这个要求和 TASK 矛盾"；一个被明确要求"只照
着改"的轻推理执行者不会。**这条流水线因此失去了一层来自执行端的冗余
校验。**

结论不是放弃这个分工，而是：**ADR-030 的定期监督在本 ADR 下变得更重要，
不是更次要。** 任何弱化监督的提议，都必须先重新评估本 ADR。

### 3a. 这个代价在第一个任务上就兑现了（2026-09-19，实例记录）

TASK-S11 的原文让 Codex 在 `risk-classify.yml` 里加一行
`require('./scripts/risk_classify_paths.js')`，并写着「其余逻辑保持原样」。
**但那个 workflow 根本没有 `actions/checkout` 步骤**——它只调 API，从不需要
仓库文件落盘。于是 PR #144 的 `classify` job 失败：
`Cannot find module '.../scripts/risk_classify_paths.js'`。

**Codex 完全照做了，指令本身是错的。** 「其余逻辑保持原样」被正确理解成
"不要加步骤"——一个高推理的执行者可能会反问"这里没有 checkout 吧？"，
一个被要求只照着改的轻推理执行者不会。这正是上面那段预言的情形。

**兜住它的是 CI，不是审查，也不是执行者。** 这一点要记准确：
§8 的重新评估条件要求四步齐全（错指令 → 照做 → 审查没发现 → 合进 `main`），
本次第四步没发生，所以**未触发重新评估**；但前三步都发生了，而唯一拦下
它的是一条机械检查。

**由此得到一条可操作的教训，写进 `docs/85` §3.1b：**
指令卡说"改这一行、其余不动"时，**必须确认那一行所依赖的前置条件已经存在**。
最容易错的正是这种"看起来只加一行"的改动——它隐含的前置（文件在磁盘上、
依赖已安装、上一步已经跑过）恰恰是执行者被明令禁止去补的。

## 4. 审查评论必须同时满足两件事

同一条 PR 评论要被两个完全不同的消费者读：

| 消费者 | 读什么 | 读不到会怎样 |
|---|---|---|
| `scripts/automerge_gate.py` | `Verdict:` 行 + 完整 40 位 head SHA + 作者写权限 | 闸门永远停在 `WAIT`，PR 不会合并，而且**不会报错**——看起来像卡住 |
| Codex | 指令卡 | 它不知道要改什么，或者自己猜 |

**这两件事缺任何一件，流水线都会静默停住而不是报警。** 格式模板见
`docs/85` §3.1。

**指令卡的粒度要求：写到 Codex 不需要思考为止。** 精确到文件路径与
函数名、新增测试连测试名和断言一起给出、要参照的现有写法直接点名文件、
每条附一句指向 TASK/ADR 的理由、并明确写出本次不做什么。具体对照表见
`docs/85` §3.1b。

理由是资源账：**ChatGPT 的额度近乎无限，Codex 的额度是稀缺资源。**
Codex 每多想一步、每多读一个文件去找答案，都在烧那份稀缺额度。
**审查侧多写三行，执行侧少烧一半。**

## 5. 硬边界：指令卡不得越过 TASK

**ChatGPT 写的修改指令，必须落在该 PR 对应 TASK 的「允许修改的文件」与
「约束」之内。**

需要越界才能修好 → **停下来，说明为什么，交给 Claude 改 TASK**，
不要在 PR 评论里直接下达越界指令。

理由：「允许修改的文件」是本仓库防范围蔓延最有效的一条护栏。如果指令卡
可以扩大它，那条护栏就从 TASK 文件漂移到了 PR 评论里——**等于没有**。
ADR-029 §7 和 ADR-030 §2 反复保住的就是这一点：**约束的定义权不能落在
下达指令的人手里。**

## 6. 返工上限：5 轮 → 3 轮

两个理由，第二个才是主要的：

1. **时间成本。** ChatGPT 是按小时轮询的，不是实时。5 轮 ≈ 5 小时。
2. **3 轮不收敛，通常说明 TASK 写错了，不是 Codex 不会改。**
   继续轮询是在用执行端的返工掩盖规格端的缺陷。正确动作是停下来，让
   Claude 改 TASK，然后重新派一次——**换个规格重来一次，比在错规格上
   磨第 4、5 轮便宜得多。**

到顶后的动作不变：停，报告具体卡点，交给 User 决定。

同时收紧的还有单条 finding 的熔断：**同一个 finding 连续 2 次修复失败就
停**（此前也是 2 次，本 ADR 不放宽）。

## 7. 不做的事

- **不让 Codex 自行判断要不要改、该怎么改。**
- **不让指令卡扩大 TASK 的「允许修改的文件」。**
- **不放宽 ADR-029 §4 的六个合并条件**，不放宽铁律 1–7。
- **不把 ChatGPT 的角色扩回"写 TASK/ADR"**（ADR-029 §7 不变）。
- ~~**不因为"Codex 现在只执行"就弱化 ADR-030 的定期监督**——理由见 §3。~~
  **2026-09-19：本条被 ADR-033 撤销**（User 要求审查改为自己触发）。
  §3 的理由（执行端没有冗余校验）**没有被反驳，仍然成立**；ADR-033 §3 主张
  它当前被"每个 PR 都由 User 人工合并"顶着，并在 §8 写明这个前提消失时
  必须恢复。**不要把本条的撤销读成 §3 已经不算数。**
- 不改变"合并由 workflow 机械执行"（ADR-029 §3）。

## 8. 重新评估条件

- **出现一次"指令卡本身是错的、Codex 照做了、审查没发现、合进了 main"**
  —— 这正是 §3 记录的代价成真，必须重新评估本 ADR，而不是只修那一次。
- 3 轮上限被频繁触顶 ⇒ TASK 的写法有系统性问题，重新评估的是 TASK 模板，
  不是把上限调回 5。
- 若 Codex 的模型档位提高到具备可靠的规格质疑能力，§2 的"不让它思考"
  可以重新评估。
- 若 ChatGPT 的额度不再宽裕，§1 的前提不成立，整条 ADR 需要重算。
