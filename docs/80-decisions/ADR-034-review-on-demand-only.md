# ADR-034: 审查完全由 User 触发；取消所有强制审计节点

- 状态: **已接受（Accepted）**
- 日期: 2026-09-19
- 决策范围: **ADR-029 §6 全节**（定时架构审计 + 三个强制人工触发节点）、
  **ADR-033 §4.2**（该节曾明确保留 ADR-029 §6 的事件闸门）、
  `docs/85` §4.0 / §4.1、`docs/83` §2 与 §10、`AGENTS.md` 角色段。
- 触发来源: User 的明确决策——"从现在开始，Claude Code 的所有审查 / 审计 /
  架构复核均改为 User 显式触发。不再存在固定频率，也不再存在'到了某个事件
  节点就强制必须叫 Claude'的规则。"目标是让 ChatGPT + Codex 连续推进更多实现，
  **积累到较大阶段后再一次性人工叫 Claude 做整体审查**。

## 1. 决定

**Claude 的审查只有一个触发方式：User 开口。**

| | 之前 | 本 ADR 之后 |
|---|---|---|
| 定时审计（每 6 小时） | ADR-029 §6 规定 | **取消**（ADR-033 已停，本 ADR 把条文一并撤销） |
| 接线真实外部系统前 | **强制**叫 Claude | **取消强制** |
| 任何生产部署前 | **强制**叫 Claude | **取消强制** |
| 一条工作线完成后 | **强制**叫 Claude | **取消强制** |
| 其他任何节点 | —— | **没有别的规则**。User 说审才审 |

**"强制"这个词从此不出现在任何与叫 Claude 有关的条款里。** 需要审查时
由 User 判断并开口；不开口就不审，哪怕 `main` 前进了几十个提交。

## 2. 本 ADR 撤销的是"必须叫 Claude"，不是"必须有人把关"

**这个区分是整条 ADR 能够成立的关键，先说清楚，避免后来者读成"闸门没了"。**

ADR-029 §6 的三个强制节点，表述是"强制人工触发一次**审计**"——
**被取消的是"必须让 Claude 审一遍"这个动作**。

**下面这些一个字没动，全部继续生效：**

- **`AGENTS.md`「禁止自主执行」整张表**——生产库 DROP/TRUNCATE、删除备份、
  销毁或回滚 VPS、轮换 `SECRET_ENCRYPTION_KEY` / `JWT_SECRET`、改 sshd /
  authorized_keys / root、改 UFW、Webshare 购买/退订/非 dry-run replacement、
  删 Cloudflare Zone 或改根域 DNS、force-push 或删 `main`、改 `AGENTS.md` 本身
  ——**每一条都仍然要求人工确认**。生产库的 `alembic upgrade` 也仍在这张表里。
- **`AGENTS.md`「灰区」条款**：不在两张表里的破坏性动作一律停下询问，
  不得自行归类为"允许"。
- **生产部署仍是人工的**，`deploy-*.yml` 的 `DRY_RUN` 闸门与人工触发不变。
- **铁律 1–8 全部不变。**
- **ADR-030 §5a 的停机/复机不对称不变**：Claude 仍可单边拉闸
  （`.github/automerge-enabled` → `false`），复机仍必须由 User 人工合并。

**所以真正的把关者一直是 User，不是 Claude。** 本 ADR 取消的是"在人批准之前
还要先让另一个 agent 看一眼"这道**附加**工序，不是"人可以不批准了"。

## 3. 诚实记下代价：被放弃的是"diff 范围看不见的东西"

不要用 §2 把代价说没了。ADR-029 §6 存在的理由写得很具体，它要查的是
**PR 级审查在结构上必然看不见**的四类东西：

1. **跨 PR 的交互缺陷**——每个 PR 单独看都对；
2. **实现与已接受 ADR 的漂移**；
3. **记忆文件过期或自相矛盾**；
4. **铁律被绕过**、补偿路径不再 fail-closed。

**这四类现在只在 User 开口时才会被查。**

而且 User 的明确意图是**攒一大批再审**，这会放大一个特定的失效模式：

> **早期的漂移会被后续所有实现当成地基。** 第 3 个提交里一条与 ADR 不符的
> 实现，如果第 40 个提交才被发现，要改的不是 1 个地方，是 37 个提交建在
> 它上面的东西。

**这不是反对这个决定**——批量审查的每提交成本确实低得多，User 的资源判断
是合理的。但**收益（省 token）和风险（改错的代价随批量增长）是同向增长的**，
这一点必须写下来，不能只记收益。

**本轮的具体佐证**：S07 一个任务里，范围闭包检查漏项**连续发生两次**
（TASK 目标点名的文件不在允许清单；`UsagePeriod.order_id NOT NULL` 影响的
既有测试不在允许清单）。两次都是**规格层**的缺陷，两次都由机械检查兜住
（一次是执行者按规则停住，一次是 MySQL 8.4 CI）。**兜住它们的都不是 Claude
的定期审查**——这是本 ADR 的一个正面论据；但同样要注意，那两次都发生在
**同一个任务内**，机械检查看得见；**跨任务的漂移没有任何机械检查覆盖**。

## 4. 保留下来的低成本补偿（都不需要 User 额外做事）

1. **健康摘要继续采集。** `.github/workflows/pipeline-health.yml` 每 2 小时
   照常写入 `pipeline-health` 分支。它无 LLM、无凭据、成本可忽略。
   **它仍然没有固定读者**（ADR-033 §5），但 User 开口审查时，它是还原现场
   最便宜的输入——不必从 `git log` 重建几十个提交的上下文。
2. **审计基线记录不取消。** `docs/83` §10 的表继续保留：每次 User 触发的
   审查，都要追加一行（日期、审计的 `main` SHA、实际跑了什么、发现了什么、
   是否拉闸）。**这张表现在的用途变了**——不再是"证明定时任务跑过"，
   而是**告诉下一次审查它的起点在哪**。批量越大，这个起点越值钱。
3. **触发审查时的标准起手式**（写给 User 和下一个 Claude 会话）：
   先读 `docs/83` §10 的最后一行拿到上次审计的 SHA，
   再看 `git log <上次SHA>..main`，
   再读 `pipeline-health` 分支上这段时间的摘要，**然后才开始看代码**。

## 5. 不做的事

- **不取消健康摘要采集**（§4.1）。
- **不取消 `docs/83` §10 的审计记录表**（§4.2）——它是批量审查的起点。
- **不放宽 `AGENTS.md`「禁止自主执行」的任何一条**，不放宽「灰区」条款。
- **不放宽铁律 1–8**，不放宽 ADR-029 §4 的六个合并条件，不放宽 3 轮返工上限。
- **不动 ADR-030 §5a 的停机/复机不对称。**
- **不把 TASK / ADR 的撰写权交出去**（ADR-029 §7、ADR-032 §3a 不变）——
  审查频率降低之后，**规格质量比以前更重要**，这条写权限边界只会更吃重。
- **不声称这样更安全。** 它更省，而且把把关责任明确收回到 User 手里。
  §3 的代价是真实的，不要在后续文档里把它稀释掉。

## 5a. 一个必须点名的冲突：自动合并的两个前提，现在只剩一个

改 `AGENTS.md` 时发现的，不写下来就等于藏起来：

> `AGENTS.md`（ADR-029 的那一段）原话：「ADR-029 同时引入了断路器与每 6 小时
> 的独立架构审计；**这两者是自动合并成立的前提，不是可选装饰**。
> 任何削弱它们的改动都要先撤销 ADR-029。」

**断路器仍在。独立架构审计，本 ADR 之后没有了。**
**按那条措辞，这属于"削弱前提"，本该先撤销 ADR-029。**

本 ADR 没有那样做，依据是一个**可以被数出来的事实**：

> **自动合并至今一个 PR 都没有合过。** #135 到 #153 全部由 User 人工合并；
> S07（#152）明确打了 `no-automerge`。**ADR-029 要防的那个风险——机器合并
> 了错的东西——至今没有发生过一次。**

所以真实状况是：**审计取消了，但它所补偿的那个风险目前是空的。**

**这是有条件的接受，不是把冲突抹掉：**

- **一旦出现第一个由 workflow 自动合并、且 User 事前未看过的 PR**，
  上面的依据即刻失效，必须二选一：**恢复独立审计，或者关掉自动合并。**
- **最省事的等效做法**：把 `.github/automerge-enabled` 保持为 `false`。
  反正每个 PR 都在人工合，关掉它不损失任何东西，却能让这个冲突彻底消失。
  **这是建议，不是本 ADR 的决定**——开关归 User。

## 6. 重新评估条件

- **出现一次"批量审查时发现某个缺陷早在几十个提交之前就已存在、且后续实现
  已建立在它之上"**——§3 预言的失效模式成真，必须重新评估批量的大小
  （不是重新评估"由 User 触发"这条）。
- 若 `docs/83` §10 的审计记录表长期没有新行（例如跨越一整个工作线仍无人
  触发审查），说明"由 User 触发"在实践中等于"不审"，需要 User 重新判断。
- 若将来某个动作被移出 `AGENTS.md`「禁止自主执行」表，§2 的论证即刻变弱
  ——**那张表是本 ADR 安全性的全部依托**，动它之前必须先回来重读本节。
